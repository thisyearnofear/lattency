## Local development

- **Always run the dev server on a random high port** (e.g. `PORT=$(( (RANDOM % 20000) + 40000 )) pnpm dev`), never the default 3000. Multiple projects share this machine and fixed ports collide; a random port avoids serving the wrong app. Echo the chosen port so it's discoverable.
- The homepage (`/`) redirects to `/london` (the default city in `lib/cities.ts`). Each curated city is served by the dynamic route `app/[city]/page.tsx`. The app degrades gracefully to bundled mock data (`lib/mock-cafes.ts`) when Base44 is unconfigured (`NEXT_PUBLIC_BASE44_APP_ID` unset), so `pnpm dev` works without any backend — including the full contribution flow (writes land in the process-local overlay, `lib/local-contributions.ts`). Set the app ID in `.env.local` to talk to the live Base44 backend.
- **`app/opengraph-image.tsx` is `force-dynamic`** — the Turbopack build-time prerender of `next/og` (satori) crashes on this Next.js 16.3 preview. Deferring to runtime keeps `next build` green and the OG image renders correctly on-demand (1200×630 PNG). When editing the OG image JSX, avoid `undefined` CSS values (satori calls `.trim()` on them — use conditional spread instead) and ensure every multi-child `<div>` has `display: flex`.

## Speed test infrastructure

- `pnpm dev` and `pnpm build` both run `scripts/gen-speedtest-blobs.ts` first, which generates `public/speedtest/download.bin` (10 MB random blob). This file is gitignored — it's reproducible from the script. If you see a "download.bin not found" error, run `pnpm exec tsx scripts/gen-speedtest-blobs.ts` manually.
- The in-browser speed test (`lib/speedtest.ts`) is client-side only. It hits three endpoints: `GET /speedtest/download.bin` (static), `POST /api/speedtest/upload` (discard), and HEAD requests to the blob for ping/jitter/loss.
- `GET /api/speedtest/whereami` returns the Vercel edge region from `x-vercel-id`. In local dev this returns `{ edge: null }` (no Vercel header) — that's expected, not a bug.
- Rate-limiting (`lib/rate-limit.ts`) uses SHA-256 hashed IPs with fixed-window counters. Backend: Upstash Redis when `UPSTASH_REDIS_REST_URL`/`TOKEN` are set (shared across instances); otherwise an in-process Map (single-instance dev). Fails open on backend errors. In local dev without `x-forwarded-for`, the check is skipped (returns `true`). To test rate-limiting locally, pass `X-Forwarded-For` header in your curl request. Five scopes: measurements (one per IP+cafe per 10min), café creation (one per IP per hour), and bounty/event/community submissions (five per IP per hour each).

## Open contribution platform (v9)

- `POST /api/cafes` creates a café + its first measurement in one flow. The measurement is mandatory — a café doesn't appear on the map without a real speed reading. This is the trust mechanism.
- `lib/cafe-metadata.ts` is the single source of truth for coffee metadata vocabulary (price tiers, milk options, seating types) and validation. Use `validateCafeMetadata()` server-side and `metadataChips()` / `formatMetadata()` for display.
- `lib/measurements.ts` contains shared pure helpers (device-type derivation, test-method provenance, input validation, outlier detection) used by both write endpoints. No DB access — pure functions only.
- `lib/local-contributions.ts` is the mock-mode write overlay. When Base44 is unconfigured, POST /api/cafes and POST /api/measurements write to this process-local store instead of crashing. Reads merge the overlay over the bundled snapshot (`lib/cafes.ts` handles the merge). Process-local only — serverless instances don't share it.
- Photos are stored as Base64 data URLs in the Cafe/Measurement entities. Production should use Base44 file storage. The contribution form resizes to 800px JPEG quality 80 client-side before upload.
- `CityId` is now `string` (not a union) to support user-generated cities. `CITIES` in `lib/cities.ts` remains the registry of curated cities with schematic layouts. User-generated cafés carry a `city` string and get transit maps generated by `computeWaypoints`.
- **Multi-city routing**: Every curated city is served by `app/[city]/page.tsx` (SSG via `generateStaticParams`). `/` redirects to the default city (`DEFAULT_CITY_ID`). Adding a city is one entry in the `CITIES` registry + `CITY_ORDER` array. The `CitySwitcher` and `TopNav` derive live cities from these automatically.
- **City-aware bounties**: `getBounties(city?)` in `lib/bounties.ts` filters bounties by city. Each fallback bounty carries a `city` field. The `BountiesBoard` component accepts an optional `city` prop.
- **Demo prefill is hidden**: The contribution form's "Try with sample data" button only appears when `?debug=1` is in the URL. Real users see "You're the first to map this area" as the empty-state CTA.

## Community board (events + communities)

- `lib/events.ts` owns both `CommunityEvent` and `Community`: validation, the process-local overlay, and the moderation gate. Everything open-submitted lands `approved: false` — the Base44 RLS read rule hides unapproved rows and `filterApprovedEvents`/`filterApprovedCommunities` re-check on read. Mock lists deliberately carry one unapproved entry each to prove the gate.
- `POST /api/events` and `POST /api/communities` accept open submissions; both carry `submitted_by` contributor attribution so `GET ?contributor=` returns the caller's own pending queue (overlay only — never leaks across contributors). `action: "approve"` in the body is a demo-only stand-in for the moderator and 403s when Base44 is configured.
- `components/events-board.tsx` renders approved events + communities per city; `event-submit-*` and `community-submit-*` are the sheet+launcher pairs, and their launchers call `router.refresh()` on submit.

### Architecture decisions

- **No `output: 'export'`** — we keep Next.js API routes as thin adapters that call Base44 SDK server-side. This preserves SSR, OG image generation, and the speedtest endpoints.
- **No Postgres, no `pg` dep, no `lib/db.ts`** — Aurora was fully retired. All former SQL paths are deleted (not flagged or proxied). The only durable backend is Base44.
- **No Auth.js** — `auth.ts` and the `/api/auth/*` routes are deleted. Base44 auth is browser-side (`lib/base44-auth.ts`). Server routes run in anonymous-contributor mode.
- **`@nimiq/core` is externalized** — `serverExternalPackages: ["@nimiq/core"]` in `next.config.ts` prevents Turbopack from bundling its WASM. It's lazy-imported inside `executeNimiqPayout()`.
- **Rate-limiting is always active** — Redis-backed when Upstash is configured, in-memory otherwise. Covers measurements, café creation, and bounty/event/community submissions. Fails open on backend errors.
- **Bounty state is durable** — `lib/bounty-state.ts` provides a lock + paid-set interface. When `UPSTASH_REDIS_REST_URL`/`TOKEN` are set, state survives serverless cold starts via Redis Lua CAS scripts. In-memory is the dev/test fallback.
- **Contributor identity is accountless** — `lib/contributor.ts` mints a local id (`contrib-…`) that rides on every write as `contributor_user_id`, and promotes to a Nimiq address when connected in the mini-app (portable identity). No login. Referrals use first-touch `?via=` attribution captured client-side and echoed on writes (`referred_by`).
- **Leaderboards, notifications, and standings are read-computed** — no cron/email. `/api/leaderboard`, `/api/notifications`, and `/me` derive their state on demand from Base44 Measurement attribution + the local trail; in mock mode they degrade to empty boards rather than crashing.
- **Bounty payments are env-gated, fail-closed** — `lib/bounty-policy.ts` `bountyPaymentsEnabled()` returns true only when the deployment can actually move money: `NIMIQ_ESCROW_ADDRESS` + `NIMIQ_PRIVATE_KEY` set (real mode), or `NIMIQ_PAYOUT_MOCK=1` (dev/test). `BOUNTY_DISABLE=1` is the kill switch — it re-pauses everything regardless of other envs, no code change needed. In a browser bundle (where server envs never arrive) the check falls back to `NEXT_PUBLIC_NIMIQ_ESCROW_ADDRESS` purely as a UI affordance; the server re-gates every request. The chain was verified end-to-end on Nimiq **testnet** (real 5 NIM escrow deposit verified by `verifyFundingTx`, POST /api/bounties → 201 `fundingStatus:"verified"`, intent retry → 200, txHash replay → 409 — see `scripts/verify-testnet-funding.ts`). Keep `NIMIQ_NETWORK=testnet` in production until real launch.
- **Nimiq PoS network ids are NOT sequential** — `lib/nimiq-payout.ts` `NETWORK_IDS` uses the Albatross values (`mainnet: 24`, `testnet: 5`, `devnet: 6`). The signature commits to the id; the old `0/1/2` values produced transactions the mempool silently dropped after broadcast. `executeNimiqPayout` now calls `tx.verify(networkId)` before broadcasting so an invalid tx (bad network, `sender == recipient`) throws instead of vanishing.
- **Bounty creation via Base44 SDK needs a service path** — the `Bounty` entity RLS is `create: {created_by: "{{user.email}}"}` and server routes run anonymously, so with `NEXT_PUBLIC_BASE44_APP_ID` configured `createBounty`'s direct `entities.Bounty.create` gets `403 Permission denied` (route 500s *after* successful funding verification). The full create flow was proven against the in-memory store; before real launch either a service-role Deno `create-bounty` function or an RLS change is required — do NOT open `create` to anonymous, since a spoofed `funding_status: "verified"` row could drain the escrow on claim.
- **Sponsor funding is verified, intent-keyed, and replay-guarded** — the funding flow: (1) the sponsor dashboard pays `NEXT_PUBLIC_NIMIQ_ESCROW_ADDRESS` via `provider.requestPayment`, then POSTs `{fundingTxHash, clientIntentId}` (a `crypto.randomUUID` minted once per funding intent); (2) the create route verifies the tx on-chain via `lib/nimiq-verify.ts` `verifyFundingTx` (executed, recipient === `NIMIQ_ESCROW_ADDRESS`, value ≥ reward in Lunas); (3) dedup on `clientIntentId` returns the existing bounty `200` — checked before the replay guard so a legitimate retry can't trip it; (4) a different intent reusing a spent `fundingTxHash` gets `409`; (5) the row is written with `funding_status: "verified"`. Rows marked `unverified` are hidden by `getBounties` and never advanced by `update-bounty-progress`. There is NO hard-coded escrow fallback — `NEXT_PUBLIC_NIMIQ_ESCROW_ADDRESS` unset disables the funding form entirely.
- **Bounty progress respects kind criteria** — `base44/functions/update-bounty-progress` (logic in `base44/shared/update-bounty-progress-handler.ts`) only counts readings the bounty's `kind` allows: `nth-contributor` counts DISTINCT contributor ids stored in `Bounty.contributing_contributor_ids`, venue-count kinds (`first-in-neighbourhood`, `attribute-match`) dedupe by café in the same field, and `tier-target` additionally requires the café's outlier-aware median to satisfy the wanted tier (`criteria: "tier-target:<tier>"`, default `express`). Unverified, expired, and already-filled bounties never advance; progress hitting target flips status to `claiming` in one write.

### Design language

## Contribution gateway (server-only secret)

- Writes to Cafe/Measurement entities now route through the `measurement-gateway` and `create-cafe` Deno functions, authenticated by a shared secret header `x-lattency-server-key` (constant-time compared). The Next.js side calls it via `lib/base44-gateway.ts` (`getBase44Gateway()`), which requires `NEXT_PUBLIC_BASE44_APP_ID` plus `LATTENCY_SERVER_KEY` (>=32 chars, server env only — NEVER `NEXT_PUBLIC_`). Both sides must carry the same private value.
- Deployed and verified on Base44 (ce01242): restrictive RLS is live — anonymous `entities.Measurement`/`Cafe` writes return 403 and reads return zero rows; `measurement-gateway`/`create-cafe` return 401 without/with a wrong `x-lattency-server-key` and serve projected fields only when keyed. Function-side secrets are registered with `npx base44 secrets set KEY=VALUE` (project-linked via `base44/.app.jsonc`, gitignored); the same value must also be set as `LATTENCY_SERVER_KEY` in `.env.local` locally and in the Vercel env for production. Seeded/direct entity writes are denied outside the gateway — do not run the existing seed script.
- **Micro-contributions (rungs 2–3, `docs/adaptive-ux-principles.md`)**: `POST /api/venues/[id]/facts` (body `{field, value, contributorId?}` — `field` must be in the `VENUE_FACT_FIELDS` allowlist, `value` validated against the shared vocabulary) and `POST /api/venues/[id]/photos` (body `{photo data-url ≤~700KB JPEG/PNG, consentPeople: true required, contributorId?}`). Both update the live Cafe record via the `venue-fact` / `venue-photo` measurement-gateway actions — `Cafe.update` under service role after a `Cafe.get` 404 check; the allowlist is the entire write surface, injected fields can't reach the entity. Rate limits: `fact` 10/hr/IP, `photo` 5/hr/IP. Vocabulary is single-sourced in `base44/shared/cafe-vocabulary.ts` and re-exported by `lib/cafe-metadata.ts`. Both routes fail closed — 503 when Base44 is unconfigured (no mock overlay); ask-card CTAs for facts/photos open `components/venue-fact-sheet.tsx` / `components/venue-photo-sheet.tsx`.

## Venue 3D capture (feature-flagged — capture run v2)

- Consent-first venue scanning per `docs/venue-3d-insights.md` / `docs/venue-3d-research.md` / `docs/venue-3d-ux-research.md`. Everything ships behind `VENUE_CAPTURE_ENABLED` (server, `lib/venue-capture-policy.ts` `venueCaptureEnabled()` — true only when the env is `"1"`) and `NEXT_PUBLIC_VENUE_CAPTURE_ENABLED` (UI affordances). Both default OFF.
- `base44/entities/VenueScan.json` — venue_id, contributor_id, capture_asset_url, consent_attestation {venue_permission, patron_notice, timestamp}, status enum (**v2**: captured → processing → preview → refining → published, with rejected / taken_down / superseded as exits), splat_url, takedown_requested, blur_verified, plus the v2 manifest fields: quality_score, coverage_sectors, face_events, supersedes_id, frame_count, frames_received. RLS is all-false; the only paths are seven `measurement-gateway` actions: `venue-scan-insert` (allowlisted fields, re-verifies both consent affirmations, forces status captured, handles supersedes_id → retires the same-venue prior scan to `superseded`, taken_down excluded), `venue-scan-get` (internal gating read: id/venue/contributor/status/supersedes only), `venue-scans` (public read — projects non-exit statuses, splat_url only when published), `venue-scan-frame` (appends {seq,ts,bytes,url} to frames_received; dedupes on seq; captured-status + contributor-match required; `url` optional + https-only), `venue-scan-finalize` (writes frame_count/quality_score/coverage_sectors/face_events; status stays captured), `venue-scan-takedown` (sets takedown_requested after venue match), `venue-scan-status` (the pipeline state machine — see below).
- API: `POST`/`GET /api/venue-scans`, `POST`/`PATCH /api/venue-scans/[id]/upload`, `POST /api/venue-scans/[id]/process`, `POST /api/venue-scans/[id]/takedown` — all 503 `VENUE_CAPTURE_PAUSED` while the flag is off. Takedown rate-limits on the `takedown` scope (5/hr/IP); frame chunks on the `scanframe` scope (300/10min per scan+IP).
- **Object storage: Vercel Blob** (`@vercel/blob`, server-only via `lib/scan-blob.ts`, gated on `BLOB_READ_WRITE_TOKEN`). Layout: `scans/{scanId}/{seq}.jpg` for capture keyframes, `scans/{scanId}/artifacts/{name}` for pipeline outputs (preview-splat.spz, poses, blur report). Everything is `access: "private"` — frames carry identifiable patrons pre-blur. `POST …/upload` validates each JPEG (magic bytes FF D8 FF, ≤512KB decoded, seq/ts shape), stores it via `putScanFrame` BEFORE the gateway manifest call (a storage failure → 503, no orphan manifest entry; retried chunks overwrite the same pathname), and the manifest entry records the returned `url`. Missing token → typed `ScanStorageError("not_configured")` → 503 "storage not configured".
- **Pipeline transitions (`venue-scan-status` action)**: strictly forward `captured → processing → preview → refining → published`; `rejected` is a QC exit from any pre-publish stage, `published → superseded` retires a scan, and `taken_down`/`captured` are never targets (the owner-veto path owns takedown). Same-status calls are idempotent (`deduped: true`). **`published` requires `splat_url` AND `blur_verified === true` in the same call — enforced in the gateway action**, not trusted to callers.
- **Worker contract (`POST /api/venue-scans/[id]/process`)**: contributor path (`{contributor_id}`) reuses the flag+crew+city gate and only moves `captured → processing`, then POSTs `{scan_id}` to `SCAN_WORKER_URL` — unset env is the honest stub (`queued: false`, scan sits at `processing`; re-POSTing retries the enqueue). Worker path: `x-scan-worker-key` header checked against `SCAN_WORKER_KEY` (≥32 chars) via the shared constant-time compare (`authorizeGateway(req, secret, headerName)`); worker-keyed requests may set processing/preview/refining/published/rejected plus `splat_url`/`blur_verified`, with the gateway state machine still the final authority. The GPU worker is `pnpm scan-worker` (`scripts/scan-worker.ts`, next bullet); `pnpm process-scan` (`scripts/process-scan.ts`) remains the operator-side pilot tool: it pulls frames via `listScanFrames`, prints the documented `deface → COLMAP → gsplat → SPZ` recipe (license-clean only), uploads a finished `.spz` as an artifact, and drives the publish chain through the worker-keyed route. `--blur-verified` is the operator's attestation that faces were blurred **before** reconstruction — the `blur_verified` publish gate exists because a splat encodes facial geometry (BIPA exposure).
- **Scan worker (`pnpm scan-worker`, `scripts/scan-worker.ts`)**: reference GPU-side daemon implementing the `SCAN_WORKER_URL` contract — a minimal `node:http` server (no deps) on `PORT` (default 8787). `GET /health` → `{ok, busy}` (unauthenticated); `POST /run {scan_id}` keyed by `x-scan-worker-key` (the same `authorizeGateway` constant-time compare, `base44/shared/gateway-auth.ts`) returns 202 and runs **one job at a time** — a second POST while busy gets 409. The job: download frames from Vercel Blob (`listScanFrames` + private `get`) → `deface` → `colmap` → `gsplat` → `spz-convert` (each `execFile`d, no shell — tool-not-found errors carry install hints; binaries via `DEFACE_BIN`/`COLMAP_BIN`/`GSPLAT_BIN`/`SPZ_BIN`, scratch via `WORK_DIR`) → uploads `final-splat.spz` via `putScanArtifact` → drives `preview → refining → published` through the worker-keyed process route, `blur_verified: true` attesting the deface step ran first. Any failure → `rejected` + a local log line; tool stderr never leaves in an HTTP response. Runbook for a GPU host: install the toolchain (`pip install deface gsplat`, COLMAP, `spz-convert`), clone + `pnpm i`, then run with env `PORT`, `SCAN_WORKER_KEY` (same value as Vercel's), `APP_URL` (the app's base URL), `BLOB_READ_WRITE_TOKEN`, `WORK_DIR`, and the `*_BIN` overrides — a Docker image with the toolchain + `pnpm scan-worker` as entrypoint is the intended recipe. Finally set `SCAN_WORKER_URL=http://<host>:8787/run` on Vercel so the enqueue POST lands on `/run`.
